# Publisher access and report corrections

A report submitted through a publisher or group form already has an ID. Administrator edits, AP revocation, bulk entry and report imports now update the existing publisher/service-year/month record through an atomic, RLS-enforced RPC. Existing IDs are retained. Rejected batches do not partially save. Entered browser work remains available after errors.

Publishers have Home, My assignments, Schedule, Report and My details pages with a visible active page. Report uses the earlier standalone form, with a persistent submitted state and an explicit correction action. The admin-approved name and Google email are read-only. Publishers edit phone, address and emergency name, relationship and phone. Birth and baptism dates, appointments and qualifications remain admin-controlled. Incomplete contact records open My details on first load; changing pages is still possible.

A Google email field on Add/Edit Publisher replaces the prominent separate login setup action. The main admin can approve or change that publisher login without changing other roles. Stale enrollment changes, foreign publishers, email reuse and transferred records are rejected. If publisher details save but login fails, the dialog explains the partial result and retains the email entry. Existing advanced account-role management is retained.

The notice-board projection preserves published program metadata, so actual part titles appear in My assignments and Schedule. Calendar reminders and the prepared private queue use 14, 7, 3 and 1 days before, at the published meeting time; absent meeting times use 09:00 in the congregation's time zone. Queue deduplication and revoked-recipient cleanup remain. Calendar files and lock-screen notification bodies contain generic text rather than publisher information. Users must import the file and allow calendar alerts. VAPID secrets, private worker invocation, physical-device permission checks and actual background push delivery remain unconfigured/unverified. No email messages are sent.

## Verification and release

Local unit/regression checks, isolated PostgreSQL contracts and Chromium checks cover failed saves, natural-key report corrections, atomic bulk/import, account isolation, email changes, transfer denial, calendar privacy and large text. Hosted acceptance adds PostgreSQL 17 backup restoration, WebKit and the wider accessibility matrix. Production deployment replaces function definitions only, takes a private definition snapshot and checks that all congregation records/drafts/publications/history and policies remain unchanged. The app's cache version is bumped and root/staging files are checked against the tested commit after Pages publishes.

Human acceptance remains necessary: a real approved Google sign-in, Realme 12 at maximum font/display sizes, iPhone Home Screen installation, a younger and older publisher completing the flows, and actual notification delivery once configured. E2EE is unchanged and inactive; no security or universal device-support guarantees are added. Public policies still await the user's requested wording changes.
